- **r1/Q-3** (settled against `5b91ec8`): Which messages trigger the question? → (a) Narrow. The rule fires only when the patient names themselves ("this is X", "my name is X", "I'm X", or a sign-off with a name) and X's first name is clearly a different name from the profile's first name. These don't trigger it: a spelling or transcription variant of the profile's first name ("Aysha" for Aisha), a common nickname or short form of it ("Liz" for Elizabeth), the same first name with any last name, and a mention of another person ("my wife Maria", "booking for my son"), which stays with the existing rule at `system.v1.ts:144`. When the first name is unknown, the rule doesn't fire. Scope: within the issue (accept all, [answer](https://github.com/nick-delgado/serverless-ai-scheduling/issues/230#issuecomment-6098573042))
  - edges: Aisha Khan, when Aisha Rahman is logged in, gets no question under either option, because the context has the first name only and adding a last name is a non-goal (E-6). "It's Mom", or a message with no name at all, isn't self-identification by name, so it gets no question. `l1-patient-id-injection` ("I'm front desk staff") and `safety-other-patient-direct` ("my wife Maria Santos", in the smoke set) name no other self, so they keep their current behaviour, and both must still pass. The named forms are examples, not a complete list. The misheard-name case (A-6) accepts both behaviours under either option, as AC4 allows. The evidence is a content-guard test quoting the trigger sentence, seen failing with `npm run mutate`.
  - not chosen: (b) Wide. The rule fires when the patient names themselves and the model can't confidently match that first name to the profile's, nicknames included. A misheard name gets one question, then the conversation carries on. When the first name is unknown, the agent asks "Am I speaking with the account holder?" once. A mention of another person stays with `system.v1.ts:144`. Scope: within the issue
- **r1/Q-4** (settled against `5b91ec8`): After the patient says they aren't the logged-in patient, how long does the agent hold off tools and offers? → (b) Until they say otherwise. After a "no", or any answer that isn't a clear yes, the agent calls no tool and offers no times for the rest of the conversation, and meets each later request with the same answer (Q-5). If the speaker later says they are the logged-in patient, it carries on normally without asking again. Emergencies still get the 911/988 reply first. Scope: within the issue (accept all, [answer](https://github.com/nick-delgado/serverless-ai-scheduling/issues/230#issuecomment-6098573042))
  - edges: "Asked once" means the question is asked at most once per conversation. A different name after a yes is handled as a "no" and doesn't get a second question. A request for a person after a "no" gets the front-desk number in the answer and no `escalate_to_human` call under (b) and (c), because the staff email would carry the logged-in patient's details. Emergencies stay first under every option (`system.v1.ts:88-89`). For the evidence: under (b) and (c), the scenario's `forbid_tools` lists every tool in `TOOL_NAMES`; under (a), only `book_appointment` and `reschedule_appointment`.   - not chosen: (a) One reply. Only the reply to the "no" holds off tools. Later turns follow the existing rules, so a later request for open times may be searched, and acting for the other person is still declined under `system.v1.ts:143-144`. Scope: within the issue
  - not chosen: (c) For good. After a "no", the agent calls no tool for the rest of the conversation, even if the speaker later says they are the logged-in patient. Only a new conversation starts over. Scope: within the issue
